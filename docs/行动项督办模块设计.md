# 行动项督办模块设计

## 1. 现有系统审计结论

- 前端：Vue 3 Composition API、Vue Router、Axios、Vite，页面位于 `vue-project/src/views`，接口封装位于 `vue-project/src/api`。
- 后端：FastAPI + PyMySQL，业务路由位于 `fastapi_backend/routers`，统一以 `/api` 为前缀。
- 数据库：MySQL，现有业务大量采用模块首次访问时 `CREATE TABLE IF NOT EXISTS` 的兼容初始化方式。
- 用户与组织：`yggl.name` 为当前系统实际用户标识，`yggl.gh` 为工号，`yggl.lsys` 为科室，`yggl.jb` 为职务/角色，`zaizhi=0` 表示在职。
- 主管领导：复用 `routers/approvers.py` 的职务匹配和部门领导规则。行动项内保存发布时确认的主管领导姓名，避免人员职务变化影响历史审批链。
- 系统角色：`webconfig.admin1` 为系统管理员，`admin2` 为人事管理员；部长/副部长、主任/副主任等角色通过 `yggl.jb` 判断。
- 附件：现有业务按模块使用独立文件目录并在数据库保存元数据。本模块采用相同模式，文件存放于 `fastapi_backend/data/action_items`，下载接口再次校验数据权限。
- 通知：现有 `notifications` 是全员更新公告，不适合个人督办；邮件能力来自 `email_sender.py` 的 `webconfig.email_address/email_auth_code`。本模块使用 `action_reminder` 保存个人站内提醒，并复用 SMTP 配置发送邮件。
- AI：现有系统管理员页已支持 DeepSeek、OpenAI 兼容网关和 Ollama。本模块新增 `action_items` 场景，可明确选择联网 DeepSeek、任一已配置的联网/兼容网关或本地模型；未单独绑定时跟随当前全局模型。
- 约束：现有后端没有统一的服务端 Session/JWT，业务接口普遍传入当前姓名再查询数据库授权。本模块沿用现状，但所有读写接口均在后端重新查询用户角色和数据范围，不依赖前端隐藏按钮。

## 2. 数据表与关系

### 核心表

1. `meeting_minutes`
   - 会议名称、类型、日期、纪要编号、主题、召集领导、发布日期、正文、原始附件、创建人、状态、AI 原始结果、AI 批次号和提取时间。
2. `action_item`
   - 行动项编号、标题、内容、来源会议、纪要原文依据、责任科室/责任人、协同科室/人员、主管领导、截止时间、实际完成时间、优先级、进度、主状态、风险状态、发布时间、AI 不确定字段、AI 批次号及审计字段。
3. `action_progress`
   - 每次填报独立新增，不覆盖历史；保存进度、本期进展、完成工作、问题、计划、预计完成时间、延期风险、填报人和时间。
4. `completion_application`
   - 每次完工申请独立新增；保存完成情况、成果、实际完成时间、遗留问题、佐证材料和审批状态。
5. `action_approval`
   - 统一保存完工、延期、负责人变更、责任科室变更、内容调整、取消等审批记录。
6. `action_change`
   - 保存变更类型、变更前后 JSON、原因、申请人、审批状态和审批结果。
7. `action_reminder`
   - 保存提醒类型、接收人、渠道、提醒时间、发送状态、催办说明和已读时间。

### 支撑表

8. `action_attachment`
   - 统一保存纪要、进展、完工、变更等附件元数据及物理路径。
9. `action_event_log`
   - 时间轴和审计日志；保存发布、接收、进展、催办、变更、完工申请、审批及人工编辑等关键事件。
10. `action_supervision_config`
   - 按经理/副经理保存多个分管科室、工作分工说明、启用状态、更新人和更新时间；配置修改同时写入全局审计事件。

### 实体关系

- `meeting_minutes 1 -> N action_item`
- `action_item 1 -> N action_progress`
- `action_item 1 -> N completion_application`
- `action_item 1 -> N action_change`
- `action_item 1 -> N action_approval`
- `action_item 1 -> N action_reminder`
- 所有业务实体均可通过 `action_attachment.business_type/business_id` 关联附件。
- `action_event_log` 以 `action_item_id` 聚合为完整时间轴。

项目当前没有独立的科室和用户数值主键，因此 `responsible_department_id` 保存 `yggl.lsys`，`responsible_person_id/supervisor_id` 保存 `yggl.name`。这是与现有模型冲突最小、历史可读性最好的落地方式。

## 3. 后端接口清单

### 元数据与权限

- `GET /action-items/permissions`：当前用户角色、操作权限。
- `GET /action-items/directory`：在职人员、科室、可选主管领导及各科室默认负责人。
- `GET /health-monitor/action-supervision-config`：系统管理员读取经理/副经理、正式科室和当前分管配置。
- `POST /health-monitor/action-supervision-config`：系统管理员批量保存分管科室及工作分工。

### 会议纪要

- `POST /action-items/minutes`：上传 `.doc/.docx`、PDF 或 TXT，解析正文并保存纪要。
- `GET /action-items/minutes`：纪要查询与分页。
- `GET /action-items/minutes/{id}`：纪要详情及关联行动项。
- `GET /action-items/attachments/{id}`：权限校验后下载附件。
- `POST /action-items/minutes/{id}/extract`：调用场景模型提取，校验 JSON 后生成草稿。
- `POST /action-items/minutes/{id}/extract/stream`：以 NDJSON 实时输出模型文本、期限归一化、Schema 校验、组织匹配、历史归档和草稿保存等工作流事件。

### AI 草稿确认

- `POST /action-items/drafts`：人工新增草稿。
- `PUT /action-items/{id}`：仅编辑未发布草稿；已发布事项必须走变更申请。
- `POST /action-items/merge`：合并草稿并保留被合并项事件。
- `POST /action-items/{id}/split`：拆分为多条草稿。
- `POST /action-items/{id}/cancel-draft`：确认页删除草稿（逻辑取消并保留审计）。
- `POST /action-items/publish`：批量校验并发布。

### 台账与驾驶舱

- `GET /action-items`：数据权限下的分页、筛选、排序。
- `GET /action-items/dashboard`：驾驶舱统计及科室分布。
- `GET /action-items/export`：按当前筛选和数据权限导出。
- `GET /action-items/{id}`：基本信息、进展、申请、审批、变更、提醒、附件和时间轴。

### 执行与闭环

- `POST /action-items/{id}/receive`：责任人接收。
- `POST /action-items/{id}/assign`：责任科室负责人在待接收阶段分配责任人。
- `POST /action-items/{id}/progress`：新增进展和附件。
- `POST /action-items/{id}/completion`：提交完工申请。
- `POST /action-items/completions/{id}/approve`：主管领导通过或退回。
- `POST /action-items/{id}/changes`：提交延期、责任人/科室/内容/取消变更。
- `POST /action-items/changes/{id}/approve`：主管领导或管理员审批变更。
- `GET /action-items/approvals/pending`：聚合当前用户待审的完工与变更申请。
- `POST /action-items/{id}/remind`：综合室人工催办。
- `GET /action-items/reminders/my`、`POST /action-items/reminders/{id}/read`：个人提醒。

## 4. 前端路由、页面与组件

- `/action-items/dashboard`：行动项驾驶舱。
- `/action-items/minutes`：会议纪要列表、上传、AI 提取入口及双栏流式日志窗口。
- `/action-items/review/:meetingId`：左文右卡 AI 确认页，支持编辑、新增、删除/取消、合并、拆分、批量设置和发布。
- `/action-items/ledger`：行动项台账、筛选、分页、排序和导出。
- `/action-items/my`：当前用户负责、协同、待更新、退回和待审批事项。
- `/action-items/:id`：行动项详情、时间轴、进展、完工、审批、变更和催办。
- `/health-monitor` 系统管理员页新增“行动项分管领导配置”，支持启停领导、复选多个分管科室并填写工作分工文本。

实现上复用统一的 `ActionItemCenter.vue` 作为驾驶舱、纪要、台账和“我的”容器，确认页和详情页保持独立，以避免改动现有公共组件。

## 5. 权限标识与数据权限

权限标识：

- `action.system_config`
- `action.minutes.manage`
- `action.extract`
- `action.publish`
- `action.supervise`
- `action.export`
- `action.department.assign`
- `action.progress.update`
- `action.completion.apply`
- `action.completion.approve`
- `action.change.apply`
- `action.change.approve`
- `action.dashboard.all`

服务端数据范围：

- 系统管理员、部长/副部长、综合技术室用户：全部行动项。
- 主管领导：本人为 `supervisor_id` 的行动项。
- 科室负责人：责任科室或协同科室为本科室的行动项。
- 责任人/协同责任人：本人负责或协同的行动项。
- 其他用户：不可读取与本人无关的行动项。
- 附件、详情、导出、审批和变更接口均再次执行相同范围校验。

## 6. 状态流转

主状态：

`草稿 -> 待发布 -> 待接收 -> 进行中 -> 待完工审批 -> 已完成`

退回路径：

`待完工审批 -> 退回整改 -> 进行中 -> 待完工审批`

取消路径：

`草稿/待发布/待接收/进行中/退回整改 -> 已取消`

约束：

- AI 提取只生成 `草稿`。
- 发布前必须人工确认标题、内容、责任科室、责任人、主管领导和截止日期。
- 只有责任人可接收、更新进展和申请完工。
- 只有已确认主管领导、部门领导或系统管理员可审批。
- 风险标签通过截止日期、最后进展时间和进展记录自动计算，不覆盖主状态：临期、已逾期、存在延期风险、长期未更新。

## 7. AI 提取接口、提示词与 JSON Schema

接口：`POST /action-items/minutes/{id}/extract`

系统提示词核心约束：

- 仅提取具有执行、落实、完成、解决、制定、推进、协调、检查等明确行动含义的事项。
- 一个段落多个独立任务必须拆分；不同责任主体承担不同任务必须拆分。
- 每条保留可在原文定位的 `source_quote`。
- 原文未明确的人员、科室、主管领导、截止日期必须返回 `null` 并列入 `uncertain_fields`。
- `deadline` 只能为 `YYYY-MM-DD` 或 `null`；年末、月底等可确定期间终点由后端安全归一化，无法确定到具体日期时置空并标记待确认。
- 不得依据常识、组织习惯或上下文猜测未出现的信息。
- 仅返回 JSON，不输出解释或 Markdown。
- 复用系统 AI 助手的 `DEPARTMENT_KNOWLEDGE` 与 `DEPARTMENT_ALIASES`，向模型提供智能制造工艺部组织结构、9 个正式科室、部办定位和科室简称。
- 模型及后端均将“水轮机室、水发室、汽发室、焊艺室、综合室、非标室、工具室、智能室、数控室、编程室”等简称归一化为人员主数据中的正式科室名称。
- “各室、各科室、所有科室、全部科室、各专业室”等表述作为全覆盖标记，后端按 9 个正式业务科室展开为独立行动项，确保每个科室可分别接收、填报和闭环。
- 展开后的每个科室以“主任、主任责、副主任”顺序确定主责任人，其余同科室主任/主任责/副主任写入协同责任人。
- 纪要未指定完成时间时，默认完成时间为会议日期后第 7 天；会议日期缺失时依次使用发布日期、纪要创建日期作为基准。

组织归属由后端在职人员目录统一校正，不依赖模型猜测：

- 责任人匹配成功后，责任科室强制使用该人员当前所属科室。
- 仅识别到责任科室、未识别到责任人时，依次按“主任、主任责、副主任”补充该科室负责人；没有符合职务的在职人员则继续标记待确认。
- 责任人为经理或副经理时，主管领导自动设置为责任人本人。
- 当前启用的分管领导配置会动态注入每次会议纪要提取提示词，不写死在代码提示词中。
- 主管领导依次按“责任人为经理/副经理本人、原文明示、责任科室唯一主管、工作分工关键词唯一匹配”确定；多名领导无法唯一判断时继续标记待确认。
- 上述规则同时应用于 AI 草稿、人工新增/编辑、批量改科室和发布前校验。
- AI 草稿保存前强制校验责任科室、责任人、主管领导、完成时间四项；任一行动项无法补齐时整批不写入，也不会提前取消旧草稿，并提示需要完善的分管配置。

JSON Schema：

```json
{
  "type": "object",
  "required": ["items"],
  "properties": {
    "items": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": [
          "title", "content", "source_quote", "responsible_department",
          "responsible_person", "collaborating_departments", "supervisor",
          "deadline", "priority", "uncertain_fields"
        ],
        "properties": {
          "title": {"type": "string"},
          "content": {"type": "string"},
          "source_quote": {"type": "string"},
          "responsible_department": {"type": ["string", "null"]},
          "responsible_person": {"type": ["string", "null"]},
          "collaborating_departments": {
            "type": "array",
            "items": {"type": "string"}
          },
          "supervisor": {"type": ["string", "null"]},
          "deadline": {"type": ["string", "null"], "description": "YYYY-MM-DD"},
          "priority": {"type": "string", "enum": ["高", "中", "低"]},
          "uncertain_fields": {
            "type": "array",
            "items": {
              "type": "string",
              "enum": [
                "responsible_department", "responsible_person",
                "collaborating_departments", "supervisor", "deadline"
              ]
            }
          }
        }
      }
    }
  }
}
```

后端先对常见自然语言期限进行安全归一化，再使用 Pydantic 二次校验；单纯的期限格式偏差不会导致整批失败。其余解析失败不会写入行动项，前端可重新提取。即使模型返回了人员或科室，后端也只接受与 `yggl` 精确匹配的在职人员和现有科室，否则置空并标记待确认。

## 8. 分阶段实施顺序

1. 数据表、权限服务、附件和审计事件。
2. 纪要上传、Word/PDF 解析、场景模型配置、AI 提取与人工确认。
3. 发布、接收、进展、完工、审批、变更和详情时间轴。
4. 台账、我的行动项、驾驶舱、导出和下钻。
5. 定时提醒、站内提醒、邮件复用和待办入口。
6. 后端语法、前端生产构建、关键权限和状态流转验证。
